# 数学实验室统一施工 SOP

日期：2026-11-08。对应设计文档：本目录 `09-unification-design.md`。这份 SOP 管“怎么做”，设计文档管“做什么”。施工前通读两份。

## 0. 角色与决定权

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 施工者（Muse 或 guoyun_liu） | 按 §2 的流程一批一批做；每批写清改了什么、基线跑了没有、真机测了没有 | 不跳过基线和真机复测；不一把梭多个步骤；不改动画文件 |
| 检查者（另一方或 Iris） | 看每批的复测结果，决定能不能合并到 main | 不凭感觉放行 |
| Iris | 决定解冻、合并、以及任何改动目标的事 | 不用管具体哪行代码 |

**冻结规则：** 冻结期间只改文档，不改代码。解冻由 Iris 一句话决定；解冻只针对她点的步骤，不是一次全开。

## 1. 开工前检查（每次开工都做，不到 5 分钟）

1. `git pull --rebase origin main`，记下 HEAD 提交号。
2. 确认工作区干净（`git status` 空）。不干净先处理，不带脏状态开工。
3. 确认基线文件在：`docs/research/lab-baseline-20261108.txt`（开场 147 条）。黄金路径基线（步骤 0 的产物）做完之前，步骤 1 及以后不开工。
4. 确认本批只做设计文档里的一步（或一步里的一批），目标写在分支名里。

## 2. 每批标准流程（9 步，每批都走一遍）

| 序 | 动作 | 做到什么算过 |
|---|---|---|
| 1 | 开分支 | 分支名 = 步骤号 + 内容，如 `unify-01-val`；不在 main 上直接改 |
| 2 | 改一层 | 只改本批的一层（值模型、或 ports、或实验数据……）；不顺手改别的东西；不动 D 的现有键（设计文档 §9 第 1 条） |
| 3 | 本地 smoke | `tools/smoke.js` 全过；新加的检查先在旧代码上验证会失败（防止假通过） |
| 4 | 跑基线 | 开场 147 条 + 黄金路径，差一个字就是回归；回归先修，不修不往下走 |
| 5 | 构建 | `tools/build-standalone.py` 重生成两个内置文件；widget < 6MB |
| 6 | 云端真机复测 | 用 commit-SHA 的 githack 链接在真浏览器里测（见 §4）；桩测试通过不算通过 |
| 7 | 合并到 main | 复测通过才合并；合并后推（`git pull --rebase` 再推，不 force-push） |
| 8 | 更新总清单 | 做完的项从 `05-all-problems-master-list.md` 里删；更新 README 状态 |
| 9 | 汇报 | 一句话：改了什么、基线过没过、真机测了什么、还剩什么 |

**一批的上限：** 一个步骤里的一批最多改一个 P 数组（实验迁移）或 8 个类型（对象模型迁移）。超了就拆。

## 3. 提交规范

- 一批一提交，提交信息写清中文做了什么，如“统一 步骤 1：值类型 Val + 维度表，空乘法器改 Q(1)”。
- 推之前先 `git pull --rebase origin main`。被拒了就拉下来再推，不 force-push（guoyun_liu 也在推，互相覆盖会丢代码）。
- 工作树必须干净再开下一批；不留半成品提交过夜。

## 4. 验证规范（什么是“验证通过”）

- **桩测试不算。** `tools/smoke.js` 的 DOM 桩测不到真机指针事件、CSS、SVG、严格模式报错，只能当第一道关。
- **真机复测是唯一标准。** 用 commit-SHA 的 githack 链接（`https://raw.githack.com/abcliu110/math/<完整SHA>/apps/web/homepage-standalone.html`），不要 main 分支镜像（缓存旧版）。每次复测写清：测了什么操作、看到了什么、过没过。
- **复测清单（每批按需勾）：** 涉及的实验开场判分对不对；改过的器材拖、连、绑、调属性对不对；练习/考试流程走得通；错题本/今天复习/家长端收没收到记录；手机/平板触屏（真机测不了触屏时写明“触屏未验”）。
- **失败处理：** 复测失败先修，修不好就回滚整批（§5），不带着已知失败合并。

## 5. 回滚规则

- 任何一批失败单独回滚（`git revert` 它的提交），不动别的批。
- 回滚后在总清单里把对应的项标回“未做”，写清失败原因。
- 连续两批回滚就停下来，先找原因，不赶工。

## 6. 基线维护

- **开场基线：** `docs/research/lab-baseline-20261108.txt`，147 个实验的开场判分结果和信号文字。统一重构每批跑一遍。
- **黄金路径基线（步骤 0 做）：** 每个实验走一遍标准解法，记录每步得分。做法：用 `tools/repro-browser.js`（已还原）的真机复现能力走标准解法，或手写 headless 脚本跑 `evaluate` + 步骤判分；记录格式与开场基线一致，存在同一目录。
- **基线只增不改：** 实验本身改了（步骤重写），对应的基线条目跟着更新，更新要写清原因；无故不改基线。

## 7. XP lint（`tools/check-xp.js`，步骤 7 之前建好）

- 检查：≥3 步、有 predict 步、why 讲推理不只给答案、不匹配信号文字（无 `.tx===` / `.tx.includes`）、不按插入顺序取器材（无 `filter(...)[N]`）、步骤 ID 是 `xpId:sN`。
- 跑法：`node tools/check-xp.js`，退出码 0 = 全过，1 = 有不过的实验（列出实验 ID 和原因）。
- 新实验不过 lint 不合并；老实验分批迁，分 P 数组分批做。

## 8. 协同（两个人同时推）

- lab builder 不碰 `anims-*.js`；动画 builder 不碰 lab 文件（`lab-nb.html`、`app.js` 实验室部分）。
- 每天开工先拉最新代码；推被拒就 `pull --rebase` 再推。
- 冲突了先停下来看 diff，不猜、不强行解决；解决不了就问 Iris。
- 每次推完在群里/对话里说一声推了什么，免得另一方基于旧代码开工。

## 9. 文档维护

- 做完一项从 `05-all-problems-master-list.md` 里删（删完数一遍剩余数）。
- 每批合并后更新本目录 `README.md` 的状态。
- 设计文档改了，SOP 里对应的流程也要改；只改一处不同步，另一处就作废。
- 研究性的新发现先写进 `research_notes/`，经过 Iris 确认后再进仓库。

## 10. 危险动作清单（做了就停工检查）

- 改 `evaluate` 的核心循环、改 D 的键、改信号文字、改 `syncBinds` 的收敛逻辑——这四项改之前，先在对话里说一声，说明为什么必须改、基线怎么兜底。
- 删文件、删实验、删器材——删之前确认没有别的代码/文档引用它（grep 全仓库）。
- widget 超 6MB——不硬塞，先拆分或瘦身。
